Core Concepts

Architecture

Hiro is a server-rendered SPA: Laravel 12 on the back end, Inertia.js bridging to a React 19 + TypeScript front end. There is no separate REST API to maintain for the UI — controllers return Inertia pages.

Request lifecycle

  • Browser requests a route → a Laravel controller resolves data and returns Inertia::render('PageName', $props).
  • Inertia ships the page component name + props as JSON; React renders resources/js/pages/PageName.tsx.
  • Subsequent navigations are XHR visits — no full page reload.

Two isolated panels

Routes are defined in routes/web.php and split into two non-overlapping areas:

PanelPrefixGateReact pages
Platform (SaaS operator)/platformrole:super_adminresources/js/pages/Platform/
Clinic (clinic staff)everything elseredirect_super_adminresources/js/pages/

A SuperAdmin is bounced out of clinic routes; clinic users cannot reach platform routes. See Roles & Multi-Tenancy.

Middleware stack

Aliases are registered in bootstrap/app.php and layered per route group:

AliasEffect
role:a,b,cGate by UserRole enum.
subscribedRequire an active ClinicSubscription.
feature:xRequire a per-plan feature flag (advanced_analytics, triage, integrations, custom_workflows).
clinic_enabledBlock users whose clinic has been disabled by a platform admin.
redirect_super_adminSend SuperAdmins to the platform panel.

One middleware is prepended to every web request — RedirectIfNotInstalled (first-run installer gate) — and two are appended: EnsureClinicExists and HandleInertiaRequests.

Shared Inertia props

HandleInertiaRequests::share() exposes data to every page: appName, clinic (with operating hours), auth.user, planFeatures, impersonating, flash, and a computed notifications feed (missed calls, cancelled/upcoming appointments). Add cross-cutting UI state here rather than per-controller.

Domain modeling

  • Enums everywhere. ~45 PHP enums in app/Enums/ model domain values (roles, statuses, call tool names, plans, etc.). Reuse the enum rather than raw strings.
  • Eloquent relationships with eager loading to avoid N+1.
  • Form Requests for validation — over 35 request classes in app/Http/Requests/.
  • Services in app/Services/ hold business logic: VapiService, VapiToolDispatcher, SubscriptionService, UsageService, InsuranceVerificationManager, ClinicProvisioner, and more.

Key subsystems

AI voice flow
VapiService + VapiToolDispatcher + the Vapi webhook controller power inbound/outbound calls and tools.
Billing
SubscriptionService + pluggable payment gateways behind PaymentGatewayManager; usage via UsageService.
Insurance
InsuranceVerificationManager fronts swappable Claim.MD / Stedi gateways.
Workflow builder
WorkflowNode / WorkflowEdge compose Vapi squads, deployed from the UI.
